# Design Decisions

## Decisions

| Decision | Reason |
|----------|--------|
| Use Python 3.12.13 for `.venv` instead of system Python 3.14.4 | `python3 -m venv` failed because `ensurepip` is missing for 3.14.4; 3.12.13 created a working venv. |
| Pin `torch==2.14.1+cu130` and `torchvision==0.29.1+cu130` from the PyTorch CUDA index | `nvidia-smi` reports CUDA UMD 13.3 and the RTX 5050 is compute capability 12.0 (Blackwell); cu130 supports this and was verified by a CUDA matmul. |
| Keep the LM Studio URL in `.env`, `.env.example`, and `src/config/settings.py` | WSL cannot reach Windows `localhost:1234`; the Windows host IP `172.19.144.1` worked, and the URL may change after a restart. |
| Try `localhost:1234` only as a configured fallback | It fails from WSL with connection refused in this environment, but keeping the fallback makes the check portable. |
| Use `google/gemma-4-e4b` with 512 max tokens for image descriptions | With 128 tokens the reply was empty because the model spent them on `reasoning_content`; 512 produced a valid one-sentence description. |
| Auto-download `yolo11n.pt` rather than committing it | `*.pt` is gitignored, and Ultralytics downloads the weights on first run. |
| Default to `yolo11s` at `imgsz=1280`, `conf=0.10`, 10 fps sampling | Step 3 tuning experiments (5/10/15 fps + conf 0.10/0.25 + yolo11n/yolo11s) showed: (a) higher fps did not reduce ID fragmentation; (b) conf 0.10 improved continuity for low-score objects (van: 109/141 at conf 0.10 vs 9/141 at conf 0.25 with yolo11n, 141/141 at conf 0.25 with yolo11s); (c) yolo11s at conf 0.10 gave the best balance (54 unique IDs, 5.96 s mean track, van fully detected). The 5 fps default was a guess that the data neither supported nor contradicted; 10 fps is the practical ceiling on this hardware (~350 ms / sampled frame decode dominates, 8–10× the YOLO time). | On `multiple_cars.jpg` it found the most cars for about 4 ms extra over `imgsz=640` (19.13 ms vs 15.22 ms) and looked most complete in visual review; `yolo11s` was not better on this image. To be re-checked on the real demo video in Step 3 against a manually counted short clip. |
| Default sampling rate: 5 frames per second of video | Tracking needs consecutive frames close together; 1 fps risks broken track IDs. The VLM still runs only on new tracks, so the extra frames do not increase VLM calls. Configurable via `SAMPLE_RATE_FPS`. |
| Simulated clock is a pure `start + timedelta(video_time)` function | No wall-clock dependence makes tests deterministic, and midnight rollover happens naturally when the offset crosses a day. |
| Use one shared `FrameRecord` for video and text modes | Downstream stages never branch on source; text mode keeps `image=None` and fills `description`. |
| Text scripts advance 60 s per `Frame N` and can name a location | A 7-line script crosses midnight while still reusing the clock, altitude and waypoint coordinates; a named location overrides the cycling route. |
| Default patrol dwell: 3 s per location | The 14 s demo then visibly cycles through gate, garage, driveway and perimeter instead of staying on gate. |
| Use Ultralytics ByteTrack through `model.track(persist=True)` | ByteTrack is already shipped with Ultralytics, so no separate tracking service is needed. `persist=True` keeps tracker IDs across the sampled frames. |
| Require 2 consecutive hits before emitting `appeared` | The real video produces many one-frame detections. A two-frame minimum removes those flickers from the event stream without delaying real objects much at 5 fps. |
| Expire tracks after 10 missing sampled frames (2 s at 5 fps) | This tolerates brief detection gaps. If the same tracker ID reappears after expiry, it becomes a fresh appearance rather than being merged with the earlier visit. |
| Treat `zone` as the drone telemetry location, not an image region | The assignment asks for events in drone patrol zones. The consequence is that every long-lived track emits a new `entered_zone` when the simulated patrol route changes, even if the object has not physically moved between image regions. |
| Map `person` to `person` and road vehicles to `vehicle`; ignore other COCO classes | These are the two object categories the analyst needs. Stop signs and other classes are filtered out before event generation. |
| Timestamp `left` at the last seen time and measure dwell to that time | Dwell should end when the object was last observed, not when the loss threshold happened to expire, so the gap is not counted as presence. |
| Write annotated video at 5 fps, maximum width 720 | The source is 2160x3840 portrait and awkward to review. 720 px wide keeps the demo small and readable, and 5 fps matches the sampled input. |
| Keep all tracked objects in the inspection summary, but only confirmed tracks in events | Flicker IDs stay visible for debugging without polluting the event stream that later stages will consume. |
| Track IDs may switch on distant moving traffic | Step 3 tuning observed tracker IDs changing for cars in the crowded far distance (different ID numbers after gaps). This is a known ByteTrack limitation on crowded scenes; confirmed tracks (min 2 frames) are stable, but short-lived distant tracks frequently reappear with new IDs. |
| Pin `lap==0.5.14` for ByteTrack | ByteTrack needs the `lap` linear-assignment package. Ultralytics auto-installed `lap==0.5.14` on the first Step 3 run, so it is now pinned for reproducible installs instead of relying on that side effect. |
| Treat zone dwell as resetting on every patrol change | The simulated drone location changes every 3 s with the current patrol dwell, so `zone_entered_at` resets each time even when the object has not moved. Step 5 should define loitering from the track's time in its current zone, and the demo should use a longer patrol dwell to reduce churn. |
| **Step 4: SQLite schema** | Three tables (`runs`, `tracks`, `events`) with indexes on `events.timestamp`, `events.track_id`, and `events(event_type, timestamp)` enable time-window and per‑track queries. All timestamps are full ISO 8601 date‑times so a window crossing midnight is an ordinary range query. |
| **Step 5: Rule-based alerts** | Four rules implemented, all reading from stored database rows only: (1) `vehicle_at_night` — confirmed vehicle track whose first-seen hour falls in the night window (default 00:00‑05:00); (2) `person_at_night` — confirmed person track in the same night window; (3) `loitering` — confirmed track whose `last_seen - first_seen` exceeds a 5‑second threshold (chosen for ~15‑20 s clips: a track present for ~1/3 of the clip is noteworthy); (4) `heavy_vehicle_logged` — any track classified as truck or bus, severity ``info`` rather than ``warning``. Only confirmed tracks (those stored in the ``tracks`` table, i.e. having received an ``appeared`` event) may trigger alerts. At most one alert per track per rule is stored, enforced by a ``UNIQUE (run_id, track_id, rule_name)`` constraint. The `entered_zone` event is ignored by all rules. Night‑window check works for timestamps on either side of midnight because only the hour component is evaluated. Shown to correctly suppress a track at 23:59:58 while firing for one at 00:00:03. |
| **Step 5 addendum: alert semantics and limits** | Alerts count *tracker tracks*, not physical objects. ByteTrack can split one object across several IDs (inflating counts) or reuse an ID (merging objects), so "6 heavy vehicles" means six confirmed truck/bus tracks, not six trucks. `person_at_night` has only been exercised on fake data because neither demo clip produced a confirmed person track. Small objects seen from altitude are often missed at `imgsz=1280`; the raw probe found far more vehicle detections than the tracker stored. Tiled/sliced inference (SAHI-style) is untried future work and is the obvious next lever if recall on small objects matters. The `tracks.frames_seen` column is misnamed: it stores the number of stored events for the track, not detected frames, and must not be used as a detection count. |
| **Step 5 addendum: run wiring** | `scripts/run_tracking.py` now runs the four rules after tracks and events are stored, so one command produces runs, tracks, events and alerts. Rules read only the database. Re-running is idempotent because `store_alert` uses `INSERT OR IGNORE` against `UNIQUE (run_id, track_id, rule_name)`, and the script prints counts queried back from the database rather than function return values.

| **Step 6: VLM on new-track crops via LM Studio** | Confirmed tracks emit an `appeared` event; the frame where that happens is the only frame a crop is saved for that track (one call per track). If the original box's shorter side is below the configurable minimum (default 20 px in source pixels), the crop is skipped with status `too_small` and no VLM call is made. A second pass over the same run sees already-stored rows and skips the VLM entirely (idempotent). Crops are saved to `data/crops/` (gitignored). Each crop is padded (default 50% of box size, minimum 4 px), clamped to the frame, then upscaled so the short side reaches 336 px while keeping aspect ratio. | |
| **Step 5 addendum: night window wrap** | The night window is defined by hour bounds and supports windows that cross midnight (for example 22:00‑05:00) by treating `start > end` as "hour >= start OR hour < end". The default remains 00:00‑05:00. |
| **Step 7: keep OpenAI settings separate from LM Studio** | The reasoning layer gets its own `OPENAI_BASE_URL` (default `https://api.openai.com/v1`), `OPENAI_MODEL_NAME` (default `gpt-5.4-mini`) and `OPENAI_API_KEY_ENV`. The LM Studio URL/model stay VLM-only. An earlier build pointed the agent at LM Studio, so "OpenAI" summaries were really local Gemma output and one contained invented track IDs. |
| **Step 7: one `OpenAIClient` for summary and ask, using `tools`/`tool_choice`** | Both commands share one client built from the OpenAI settings. Requests use the current `tools` + `tool_choice="auto"` API instead of the removed `function_call` field, and automatic tool choice lets the model fetch only the stored text it needs. No global `openai.*` call remains. |
| **Step 7: compact JSON with explicit truncation, never silent slicing** | Tool results return a `total`, `showing`, a `truncated` flag and a "showing N of M" notice when long (default row limit 50). The old `alerts[:5]`-style truncation hid data from the agent; explicit metadata keeps the model honest about what it did not see. |
| **Step 7: cost guard and running total live in SQLite** | Every chat call records prompt tokens, completion tokens and estimated cost in `agent_costs`; the running total is queried back from the table, not kept in process memory, so a new command sees earlier spend. A warning is logged at $0.50 and a new call is refused at $1.00. |
| **Step 7: one summary per run, `--force` for a fresh call** | `run_summaries` caches one summary per run and returns it without a model call. Re-running with `--force` regenerates it, which is how the two final real summaries were produced after cached rows already existed. |
| **A stale shell variable can override `.env`** | `load_dotenv` does not overwrite a variable already exported in the shell, so a rotated key written to `.env` is ignored while an old `OPENAI_API_KEY` remains in the environment. This caused the earlier key problem. The check compares the shell value with the `.env` value and stops when they differ; `unset OPENAI_API_KEY` clears the stale value before a fresh run. |
| **Step 8: `agent_traces` table records answers, not calls** | One row per user-visible answer: run, mode (`summary`/`ask`), question (NULL for summary), tool calls as JSON (`name`, `arguments`, `result_size`), the answer text exactly as shown, model name, prompt/completion tokens, estimated cost, latency in ms, created time, and a `cached` flag. Cached summaries get a row with zero tokens so every answer is auditable. `agent_costs` stays the billing ledger; traces are the answer audit. `record_agent_trace` commits inside itself, and no key or request headers are ever stored. |
| **Step 8 follow-up: ask prompt declares the digest partial and requires a tool call** | On real OpenAI the model never chose a tool: for track 47 (a car, not in the preloaded truck-only digest) it listed 2 items, one an alert rather than an event, and said "the data cannot tell" although 10 events existed. Fake-client tests could not catch this because they script the choice. The prompt-only fix states exactly what the digest covers (alerts, truck-class tracks and their events, descriptions, event counts), requires a matching read-only tool for anything else, forbids "the data cannot tell" before trying a tool, says alerts are not events, and adds `{run_id}` to the ask user template. The tool loop and round cap of 4 were deliberately left unchanged; `tool_choice` stays `auto`. |
| **Frame index: one row per detection, not one per confirmed track** | The brief requires a frame-by-frame index queryable by time or object. `frames` has one row per sampled frame (full ISO timestamp, telemetry zone, `detection_count`, nullable `description` for text mode); `frame_objects` has one row per detection (nullable `track_id`, class, confidence, JSON bbox). Storing only confirmed tracks would discard real one-frame detections and make `detection_count` disagree with the stored object rows. Consequence: the index legitimately contains IDs that never reach `tracks`, and a track's frame-by-frame class votes can differ from its stored class, so "truck frames" may include a few IDs listed as `car` in `tracks`. These are reported, never filtered out. |
| **Backfill ID check is one-way** | The first implementation required set equality between frame-index track IDs and `tracks`; run 1 failed with extras `[113, 131]` — single-frame car detections with no `appeared` event. The human chose option (a): every confirmed ID in `tracks` MUST appear in the frame index (fail and stop otherwise), while frame-only IDs are allowed and printed as `unconfirmed_detections` with count and IDs. No rows are dropped to force a match. Run 1 passes with 2 extras; run 2 passes with 2 extras `[5, 592]`. |

## Step 9A: Streamlit app (read-only UI)

- **Read-only by construction.** `app/data.py` opens SQLite with a `mode=ro` URI and all pages call only existing `src.storage` queries. The only writes to `data/demo.db` come from the two agent buttons, which go through the existing `cmd_summary` / `cmd_ask` commands; the UI does not duplicate prompts, tool loops, tracing or the cost guard.
- **Typed data layer.** Query wrappers return small dataclasses (`RunInfo`, `AlertView`, `Provenance`, `TraceView`, …) so pages never handle sqlite rows and the layer is tested without importing Streamlit. `frames_seen` is deliberately re-counted from events for the track panel because that column is a historical misnomer.
- **Provenance panel.** Selecting an alert shows its stored reason, the track row, the full event timeline, the saved crop (or a placeholder when the file is missing / the crop was `too_small`), the VLM status/description/latency and the run's tuning settings. The timeline repeats that zone changes are simulated drone locations, not object movement.
- **"Questionable" badge means one thing only:** the track ID appears in the `questionable` array of that run's stored `run_summaries.text`. It is not a fresh model judgement and never triggers a model call.
- **Summary rendering.** Stored summaries are JSON; the app parses and displays `summary`, `notable_alerts` (table), `questionable` and `recommendations` as text, never the raw JSON string. If no summary exists, the page states the expected upper-bound cost (4k prompt allowance plus the configured output ceiling) and the running total against the cap; the agent's own guard is authoritative.
- **Ask gating.** Text box and buttons are disabled with an explicit reason when the OpenAI key is absent or the SQLite-backed running total has reached the cap. Key presence is checked as a boolean only; no key or header is printed or stored by the UI.
- **Plain default styling:** no custom theme, CSS or component library; only standard Streamlit widgets. The app is started from the repo root with `streamlit run app/streamlit_app.py`; `app/streamlit_app.py` inserts the repo root into `sys.path`, the same fix used by `scripts/ask_agent.py`.

## Step 9B: visual direction (shape note)

**Design read:** an Operate-mode security console for a reviewer and a screen-recording hiring reviewer, with a calm, dense, evidence-first language, leaning on native Streamlit structure plus a single token-driven CSS layer — no marketing voice.

Dials: `DESIGN_VARIANCE 3`, `MOTION_INTENSITY 2`, `VISUAL_DENSITY 7`. The information is the interface; decoration must not compete with it.

- **Tokens in one place:** `app/styles.py` is the only source of colour, type, spacing, radius and state rules. Both themes come from one semantic token set; the DOM carries a `data-theme` attribute. Streamlit 1.67.0 themes natively only at startup through `.streamlit/config.toml`, so the in-app toggle is a CSS-injection switch; this is stated plainly in the report alongside any element that does not follow it.
- **One accent:** restrained teal (`#5BA6B8` dark fill, `#176C7B` light fill) for the single primary action and current selection. Severity uses amber (warning) and blue (info) only; green/red are reserved for status, never decoration. No purple-to-blue gradients, no glow, no emoji headings.
- **Type:** system sans for prose and labels, monospace with `font-variant-numeric: tabular-nums` for IDs, timestamps, counts and costs. No network font loading. Fixed rem scale, 1.125–1.2 ratio between steps.
- **Shape:** sidebar holds brand, run, navigation, theme switch and a simulated-clock footer. A compact context strip in the main area keeps the selected run visible when the sidebar is collapsed. Tables use hairline separators rather than stacked cards; no card nested in a card, no icon tiles above headings.
- **States:** every control has default, hover, focus-visible, active and disabled definitions in both themes; minimum 40 px control height, 4 px control radius, 2 px panel radius, spacing scale 4/8/12/16/24/32.
- **Honesty limits:** simulated time/zones and "alerts count tracks, not objects" stay visible on the main surface of every page, not only in docs.

### Step 9B implementation decisions and repairs
- **Runtime theme toggle is CSS injection, not native Streamlit theming.** Streamlit 1.67.0 only reads `[theme] base` from `.streamlit/config.toml` at process start; there is no supported runtime theme API. `app/styles.py` injects one stylesheet through a same-origin component script and sets `data-theme` on `<html>`. All semantic tokens, tables, badge, timeline and crop-image frames follow it. Native Streamlit chrome that still ignores CSS variables: the sidebar expand/collapse icons and the radio/switch thumb are drawn by Streamlit's own design system; their surrounding surfaces and focus rings do follow the tokens, and the component iframe emits a benign sandbox warning in the browser console.
- **Tables use `st.table`, not `st.dataframe`.** The dataframe is canvas-backed and paints its own light-mode text, so it cannot be rethemed; the static HTML table renders with the same tokens in both themes. Row counts are small (a few dozen), so the loss of virtualisation is not material.
- **P1 repairs found by render checks:** the first CSS hid the whole `stHeader`, which also hid the sidebar expand button; hiding only toolbar actions fixed it. Context `<code>` chips inherited a white browser background in dark mode; they are now transparent. Table cells had Streamlit's dark-on-light text colour; they are now overridden from semantic tokens. All three were verified by re-screenshot.
- **No module hot reload for edits to imported files.** Streamlit watches the entry script, not imported modules; after each `app/styles.py` or page edit the server was restarted before taking screenshots. This is a workflow note, not an app behaviour.
- **`st.badge` needs a direct class override.** Streamlit 1.67 emits `.stMarkdownBadge` with inline light-mode colours and no `data-testid`, so the questionable-alert badge was identical in both themes until a semantic-token rule with `!important` targeted that class. The other badges use tokens via our own `.ops-chip` classes.
